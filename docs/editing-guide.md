# 글 다듬기 가이드

Tistory 형식에 맞추느라 어색해진 글을, 글쓴이가 머릿속에 그렸던 생각이 깔끔하게 드러나도록 다듬기 위한 기준입니다. 앞으로 새 글을 쓸 때도 같은 기준을 따릅니다.

## 1. 반드시 지킬 것 (바꾸지 않음)

- **사실은 그대로**: 날짜, 점수, 수치, 시험명, 회차, 기관명, 사람 이름, 코드, 실행 결과, 인용문은 바꾸지 않는다.
- **없는 내용을 만들지 않는다**: 글쓴이가 쓰지 않은 경험, 감정, 의견, 사실을 덧붙이지 않는다. 문장을 다듬는 것이지 새로 쓰는 것이 아니다.
- **글쓴이의 목소리**: 1인칭 시점과 문체를 유지한다. 에세이가 "~다"체면 "~다"체로, 공부노트가 "~합니다"체면 "~합니다"체로. 한 글 안에서는 한 가지 문체로 통일한다.
- **주소(폴더 이름)와 머리말의 category, subcategory, date, tistoryId**는 바꾸지 않는다.
- **이미지와 링크**는 지우지 않는다. 구글 드라이브 링크도 지금은 그대로 둔다 (별도 결정 대기).

## 2. 고칠 것

### 구조
- 본문에 `#`(h1)을 쓰지 않는다. 큰 단락은 `##`, 그 아래는 `###`. 단계를 건너뛰지 않는다.
- 제목 번호 매기기는 글 안에서 한 가지 방식으로 통일한다 (예: `## 1. ...` 또는 번호 없음).
- 글 안에 손으로 만든 목차나 "바로가기" 목록은 지운다. 넓은 화면에서는 오른쪽에 목차가 자동으로 생긴다.
- 한 문단에는 하나의 생각. 너무 긴 문단은 나누고, 한 줄짜리 문단이 잘게 흩어져 있으면 합친다.
- 나열은 목록으로, 비교는 표로. 반대로 목록이 과하게 쪼개져 읽기 어려우면 문장으로 잇는다.

### Tistory 흔적 정리
- 의미 없는 인사말과 상투적인 시작("안녕하세요, 오늘은 ~에 대해 알아보겠습니다")은 글쓴이 고유의 표현이 아니면 줄이거나 바로 본론으로 시작한다. 마무리 인사("도움이 되셨으면 좋겠습니다")도 마찬가지로 줄인다. 단, 글쓴이의 개성이 담긴 인사는 남긴다.
- 강조가 남발된 곳(문장 전체 굵게, 연속 굵게)은 핵심 단어만 남긴다.
- HTML 태그(`<strong>`, `<span>`, `<br>`, `<p>`)는 Markdown으로 바꿀 수 있으면 바꾼다. 표 안의 줄바꿈 `<br>`이나 병합 셀 표처럼 Markdown으로 표현할 수 없는 것은 남긴다.
- 강조 상자는 한 가지 형식으로 통일한다:
  ```md
  > **핵심 요약**
  >
  > 내용
  ```
- 빈 줄 여러 개, 의미 없는 구분선(`---` 남발), 공백만 있는 문단은 지운다.

### 문장
- 맞춤법, 띄어쓰기, 오탈자를 고친다.
- 같은 말을 반복하는 문장, 군더더기 표현("~하는 것 같습니다" 남발, "정말 정말")은 덜어낸다. 단, 글쓴이의 말버릇이 글의 맛인 경우는 살린다.
- 문장이 너무 길면 나눈다. 주어와 서술어가 어긋난 문장은 바로잡는다.
- 이모지와 이모티콘은 쓰지 않는다. 원문에 있으면 지우거나 글로 바꾼다 (예: 전화 아이콘 → "전화").

### 머리말
- `title`: 오탈자, 띄어쓰기만 고친다. 의미가 바뀌는 수정은 하지 않는다.
- `description`: 검색 결과와 글 목록에 보이는 한두 문장 요약. 본문 첫 줄을 잘라 쓴 것이면 글 전체를 대표하는 요약으로 새로 쓴다. 120자 안팎, 마침표로 끝낸다.
- `tags`: 이번 작업에서는 건드리지 않는다.

### 이미지
- 대체 텍스트(`![여기]`)가 비어 있으면 사진 내용을 짧게 적는다 (예: `![SCPC 본선 행사장 입구]`). 사진에서 확실히 알 수 없는 것은 추측하지 않는다.

## 3. 결과물 확인

- `npm run build`가 에러 없이 끝나야 한다 (머리말 형식, 깨진 링크 확인).
- 원문과 비교해 사실, 코드, 이미지, 링크가 빠지지 않았는지 확인한다.

## 4. 시범 작업에서 정한 추가 원칙

- **바꿀 이유를 댈 수 없으면 바꾸지 않는다.** 이미 깔끔한 글은 최소한만 고친다.
- **기술적으로 틀린 내용은 바로잡는다** (사용자 승인, 2026-11-21). 확실히 틀린 것만 고치고, 고친 곳은 작업 보고에 모두 적는다. 애매하면 고치지 않고 보고한다.
- **시험 대비 공부노트는 시험 기준 서술을 유지한다.** 실제 DBMS나 실무와 다르더라도 시험에서 정답으로 인정되는 내용이면 그대로 둔다 (예: 정보처리기사 SQL 정리).
- **description 문체는 글의 문체를 따른다.** 에세이는 "~다"체, 공부노트·후기는 "~합니다"체.
- **문장 중간의 " - "** 는 문장을 끊거나 쉼표로 바꾼다. 줄표(—)는 쓰지 않는다.
- **외래어 표기**는 국립국어원 표기를 따르되, 글쓴이가 일관되게 쓰는 표기는 존중한다.
- **사진 위치**: 사진은 관련 문단 바로 뒤로 옮겨도 된다. 캡션(사진 아래 기울임 줄)의 형식과 내용은 유지하고, 사진과 맞지 않아 보이면 고치지 않고 보고한다.
- **고유명사**: 공식 명칭과 표기를 따른다 (예: SCPC, Codeground, 서울R&D캠퍼스).
- **소제목**: 시간 순서로 읽히는 짧은 후기·수필(대략 10문단 이하)에는 새로 소제목을 넣지 않는다.
- **시제**: 지난 일을 돌아보는 글은 과거형을 기본으로 하되, 지금도 그런 것(현재의 생각, 지금 가진 물건)은 현재형으로 둔다.
- **확인이 필요한 곳**은 본문에 주석을 남기지 않고 작업 보고에만 적는다.
- **한국어 굵게 표시**: 닫는 `**` 바로 앞이 문장부호이고 바로 뒤에 한글 조사가 붙으면 굵게가 깨진다. 범위를 옮기거나(`**UNKNOWN**(거짓)이`) `<strong>`을 그대로 둔다.
- **공부노트**: 본문 속 SQL과 코드는 인라인 코드로 쓰고 `\*`, `\_` 같은 이스케이프를 없앤다. 표나 목록을 인용 상자 안에 넣지 않는다. 코드 블록과 표의 캡션은 기울임 한 줄로 통일한다.
- **코드 블록 검증**: 원문(`git show HEAD:경로`)과 수정본에서 코드 블록만 뽑아 비교해, 한 글자도 바뀌지 않았는지 확인한다.
